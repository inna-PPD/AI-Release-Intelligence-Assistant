# Правила розмітки golden set (DefectReport)

Golden set — еталон, з яким порівнюються відповіді моделей. Правила однакові для всіх записів;
якщо випадок неоднозначний — рішення фіксується тут, а не «на око».

## Загальне
- Розмічаємо **лише те, що є в тексті** або однозначно з нього випливає. Не вгадуємо.
- Немає інформації → `null` (для списків — `[]`).
- Назви й цитати — **мовою оригіналу**, як у тексті (без перекладу).

## Поля

| Поле | Правило |
|---|---|
| `title` | короткий підсумок проблеми мовою оригіналу. **Не входить у field accuracy** — вільний текст, перевіряється вручну |
| `is_defect` | `true`, якщо описано некоректну поведінку (включно з known issue з release notes); `false` — побажання, запит на функцію, питання |
| `components` | усі компоненти рішення, названі в тексті або однозначно визначені. `name` — як у тексті (`cnt_invoice`, `Approval Flow v2`, `pac solution pack`); якщо тип зрозумілий, а назви немає — `name: null`. Якщо компонент не визначити — не додаємо |
| `components.type` | таблиця Dataverse → `table`; Power Automate → `cloud_flow`; pac CLI / pipelines / build tools → `alm_tooling`; імпорт/експорт solution → `solution`; LEO PPM / Gantt → `leo_ppm` |
| `environments` | лише середовища, **де відтворюється** проблема, названі явно (`прод`, `PROD` → `prod`; `уат` → `uat`; `тест` → `test`). «На деві все ок» — dev не додаємо. Середовища клієнтів у GitHub-текстах без назв dev/test/uat/prod → `[]` |
| `severity` | явна позначка (`Severity: High`, `sev med`, `low priority`, `Low impact`) або однозначні фрази: «критично», «блокує деплой/реліз» → `critical`. Емоції без оцінки впливу («!!!», «дірка») → `null`. Якщо серйозність змінилась («high (було), зараз low») — поточна |
| `release_version` | версія продукту/рішення, в якій спостерігається проблема. Якщо автор не впевнений («вроді 1.5.1») — все одно беремо. Якщо версій кілька — та, де проблема є (не та, де «працювало») |
| `steps_to_reproduce` | лише **послідовність** дій (нумерований список, стрілки, «зробив → потім»). Одна дія-умова («при імпорті солюшена») → `[]`. Формулювання — як у тексті |
| `expected_result` | лише якщо очікувана поведінка описана явно |
| `actual_result` | що сталося насправді / текст помилки |
| `is_regression` | `true`, якщо сказано або однозначно випливає, що раніше працювало («в 1.5.0 було ок», «з 12.10 не підтягуються», «до оновлення такого не було»); `false` — лише якщо явно сказано, що ніколи не працювало; інакше `null` |

## Склад golden set (10)

| Група | Записи | Чому |
|---|---|---|
| Синтетичні «чисті» (шаблон DevOps) | syn-001, syn-010 | базова перевірка |
| Синтетичні «брудні» | syn-005, syn-009, syn-017 | суржик, емоції, неявна регресія, кроки в оповіді |
| Пастки | syn-018 (known issue у release notes), syn-020 (побажання, не дефект) | `is_defect`, `severity` з тексту |
| Реальні GitHub | gh-005, gh-012, gh-019 | дві версії в одному тексті, регресія між версіями pac CLI, довгі кроки |

Golden set **не використовується** як приклади (few-shot) у промптах — інакше метрики завищені.

## Процес
1. Чернетку розмітки підготовлено з допомогою LLM (`"reviewed": false`).
2. Автор вручну перевіряє кожне поле за цими правилами, виправляє і ставить `"reviewed": true`.
3. Через день — повторна перевірка 3 випадкових записів.
