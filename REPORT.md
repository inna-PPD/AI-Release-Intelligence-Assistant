# REPORT — кейс 2: RAG на власних даних + Evals

> AI Release Intelligence Assistant · етап 2 · 12.11.2026
> Звіт кейсу 1 (structured extraction) — [reports/REPORT_case1.md](reports/REPORT_case1.md).

**Що зроблено:** 42 документи (HTML, Markdown, DOCX, PDF) → очищення й дедуплікація → 404 чанки за структурою документа → embeddings (`embeddinggemma-300m`, локально) у Qdrant + BM25 → hybrid search + reranker (`bge-reranker-v2-m3`) → відповідь `gpt-4o-mini` з джерелом для кожного твердження і «не знаю» → тестсет із 23 питань, детерміновані перевірки + LLM-суддя (`claude-haiku-5.5`) + faithfulness → поріг у GitHub Actions.

Відтворення:
```bash
python main.py ingest           # корпус → data/processed/chunks.jsonl
python main.py retrieval-eval   # якість пошуку → evals/results/retrieval_metrics.md
python main.py rag-eval         # якість відповідей → evals/results/rag_metrics.md
python main.py calibrate        # згода судді з ручною розміткою → evals/results/judge_calibration.md
```

## 1. Метрики пошуку (retrieval)

25 питань з відомим правильним чанком (15 базових + 10 складних, усі перевірені вручну). Hit = у top-k є чанк потрібного документа, що містить ключову фразу. Повна таблиця — [evals/results/retrieval_metrics.md](evals/results/retrieval_metrics.md).

| Chunking | Пошук | recall@1 | recall@5 | MRR@10 | Складні (10): MRR |
|---|---|---|---|---|---|
| fixed 300/50 | vector | 0.64 | 0.88 | 0.74 | 0.73 |
| structure | vector, без промптів моделі | 0.52 | 0.92 | 0.71 | 0.62 |
| structure | vector | 0.72 | 1.00 | 0.83 | 0.75 |
| structure | BM25 | 0.64 | 0.84 | 0.71 | 0.56 |
| structure | hybrid (RRF) | 0.84 | 0.92 | 0.89 | 0.91 |
| fixed 300/50 | hybrid + rerank | 0.80 | 0.96 | 0.88 | 0.79 |
| **structure** | **hybrid + rerank** | **0.96** | **1.00** | **0.97** | **0.93** |

**Висновки:**
- Кожен крок дає виміряний внесок: структурний chunking (+0.09 MRR проти fixed за вектором), промпти embedding-моделі (+0.12), hybrid (+0.06), reranker (+0.08).
- На **складних** питаннях (той самий текст у різних релізах, однаковий параметр у різних командах) hybrid дає найбільший приріст: 0.75 → 0.91. Базові питання цього не показували — після фідбеку на чекпоінті їх доповнено складними.

- **Детерміновані перевірки** — без LLM: статус `not_found` для питань без відповіді; doc_id процитованого чанка ∈ очікуваних джерел; ключові факти (з альтернативами: «щомісяця \| monthly»); кожне твердження в `claims` має id джерела.
- **LLM-суддя** — інша модель, ніж генератор (`claude-haiku-5.5` проти `gpt-4o-mini`): correct / partial / incorrect відносно еталона. Калібрування на ручній розмітці — розділ 3.
- **Faithfulness** — той самий суддя перевіряє кожне твердження: чи підтверджують його процитовані джерела.
- **Latency** — в основному локальний reranker на CPU (~8 с); LLM-виклик — 2–4 с.
- **Вартість судді** — $0.006 за прогін 23 питань.

**v1 → v2.** У v1 faithfulness була 0.84 при правильності 0.97: відповіді правильні по суті, але **сильніші за джерела**. Промпт v2 додав правило «формулюй рівно настільки сильно, як у джерелі» ([CHANGELOG](prompts/rag_answer/CHANGELOG.md)). Faithfulness зросла до 0.87, і CI проходить. Але приріст невеликий і частково шумовий (див. помилки 2–3): правило модель виконує не завжди, а суддя на тому самому формулюванні двічі дав різні оцінки. Еталони й суддю між v1 і v2 не змінювали, щоб не «підганяти» поріг.

## 3. Калібрування LLM-судді

Аркуш [evals/calibration/hand_grades.json](evals/calibration/hand_grades.json) — 17 відповідей v2 без вердикту судді (щоб він не впливав на людину). Автор оцінює їх за тими самими правилами ([prompts/rag_judge/v1.md](prompts/rag_judge/v1.md)), `python main.py calibrate` рахує згоду.

Результат — [evals/results/judge_calibration.md](evals/results/judge_calibration.md):

| Метрика | Значення |
|---|---|
| Оцінено вручну | 17 відповідей v2 (16 correct, 1 partial) |
| Точний збіг вердикту | **94%** (16 / 17) |
| Збіг «правильно / неправильно» | 94% |
| Cohen's κ | **0.64** (суттєва згода) |

**Процес.** Перша ручна оцінка — усі 17 correct (згода 88%, κ = 0.00: при одній категорії κ не інформативна). Після перегляду двох розбіжностей автор змінив оцінку t09 на partial — власне рішення, з приміткою: «немає згадки, що зміни оголошуються в release notes на GitHub». Оцінку t16 лишив correct.

**Єдина розбіжність — t16** (середовища для ALM): людина — correct, суддя — partial («пропущено окремі середовища розробки»; у відповіді вони згадані лише побіжно — «тестове середовище, відокремлене від розробки»). Суддя суворіший за людину — для порогу CI це безпечний напрям помилки.

**Що виявило калібрування про суддю:** на t09 суддя назвав «недоведеним» твердження про оновлення раз на три місяці, хоча воно є в джерелах (S2, S5 — це підтвердила перевірка faithfulness). Суддя правильності бачить лише еталон, а не документи, тож додаткові коректні факти може вважати вигадкою. Вердикт partial при цьому збігся з людським — але з іншої причини.

**Обмеження:** у вибірці немає неправильних відповідей, тож не перевірено, чи суддя ловить хибні відповіді. Наступний крок — додати до калібрування навмисно хибні й неповні відповіді (напр. з застарілої інструкції 1.4) і оцінити їх вручну.

## 5. Що покращити далі

1. **Перевірка faithfulness у пайплайні, а не лише в evals:** непідтверджене суддею твердження → одна спроба переформулювати (як repair у кейсі 1). Помилки 1, 2, 4 це закривають.
2. **Сильніша модель-генератор для формулювань** (порівняти gpt-4o-mini з дорожчою на тому самому тестсеті — інфраструктура вже є) або менша `temperature` правил через few-shot приклади поза тестсетом.
3. **Поріг «не знаю» з урахуванням кількох кандидатів**, а не лише найкращого, і окремо для перефразованих питань; додати в тестсет більше питань-«двійників» (як u01, u02).
4. **Калібрування судді на збалансованій вибірці:** зараз 17 ручних оцінок (16 correct, 1 partial; згода 94%, κ = 0.64), неправильних відповідей немає. Додати навмисно хибні й неповні відповіді, 30+ оцінок і другого анотатора; кілька прогонів судді з голосуванням, щоб прибрати нестабільність (помилка 3).
5. **Швидкість:** reranker на CPU — основна частина latency (p95 16 с); кеш reranker-оцінок для повторюваних питань або GPU для сервісу (кейс 4).
6. **Тестсет:** 23 питання — мінімум; розширити до 50+, додати питання з кількома правильними документами та prompt injection у документах.

## 6. CI

[.github/workflows/evals.yml](.github/workflows/evals.yml): на кожен push у `main` і pull request — `pytest`, потім `python main.py rag-eval --ci`. Прогін падає, якщо будь-яка метрика нижче порогу з [config/rag.yaml](config/rag.yaml) → `evals.thresholds`. Моделі fastembed кешуються між запусками, embeddings чанків уже в репозиторії. Метрики потрапляють у Job Summary, повні результати — в артефакт `rag-eval-results`. Потрібен секрет репозиторію `OPENROUTER_API_KEY`.
