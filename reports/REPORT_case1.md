# REPORT — кейс 1: Structured Extraction Service

> AI Release Intelligence Assistant · етап 1 · дані станом на 18.10.2026
> Відтворення: `python main.py run` (усі прогони) → `python main.py eval` (метрики → `results/metrics.md`)

## 1. Задача

Сирий баг-репорт про рішення на Microsoft Power Platform (Teams, email, Azure DevOps, GitHub issue) → валідний JSON за схемою [`DefectReport`](src/schema.py): 10 полів, 3 enum (тип компонента, середовище, серйозність), вкладений список `components[{type, name}]`.

**Дані:** 40 текстів — 20 знеособлених GitHub issues (`microsoft/coe-starter-kit`, `microsoft/powerplatform-build-tools`) і 20 синтетичних (вигадана компанія Contoso; українська, англійська, суржик, пропущені поля, не-дефекти). Жодних корпоративних даних.

**Golden set:** 10 текстів, стратифікований відбір (чисті, «брудні», пастки, GitHub), розмічено за [правилами](data/golden/ANNOTATION_GUIDE.md) і перевірено вручну.

## 2. Що порівнювали

| Вимір | Варіанти |
|---|---|
| Модель | `openai/gpt-4o-mini` через OpenRouter (strict structured output) · `qwen2.5:7b-instruct` локально через Ollama, RTX 3060 Laptop (схема в `format`) |
| Промпт | [`v1`](prompts/extract_defect/v1.md) — baseline · [`v2`](prompts/extract_defect/v2.md) — пояснення enum і правила для полів ([CHANGELOG](prompts/extract_defect/CHANGELOG.md)) |
| Семплінг | A: `temperature=0, top_p=1` · B: `temperature=0.7, top_p=0.9` |
| Контрольний прогін | `qwen2.5:7b-instruct+json-mode` — та сама модель без схеми в `format` (лише «поверни JSON»), щоб перевірити валідацію і repair |

**Як рахуються метрики** ([src/evaluation/metrics.py](src/evaluation/metrics.py)):
- **Field accuracy** — середнє по 10 полях на golden set. Enum, bool і версія — точний збіг; списки — збіг множин; назви компонентів і кроки — нечіткий збіг (F1); `expected_result` / `actual_result` — покриття слів еталону ≥ 50%. `title` не оцінюється (вільний текст). `failed` = 0 по всіх полях.
- **% валідних** — відповідь пройшла Pydantic-валідацію з 1-ї спроби (`ok`) або після однієї спроби виправлення (`repaired`).
- **Latency p50 / p95** — по всіх 40 текстах, включно з repair; локальна модель прогрівається перед прогоном.
- **Вартість на 1000 документів** — з фактичних токенів відповіді × ціна OpenRouter на 18.10.2026 ($0.15 / $0.60 за 1M вхідних / вихідних). Для локальної моделі — $0 API (без урахування електрики й заліза).

### 3.3. Що видно з цифр

1. **Промпт важить більше, ніж вибір моделі в межах класу.** v1 → v2: gpt-4o-mini +0.18, qwen +0.14. Найбільший приріст — `components.type` (0.30 → 0.80): у v1 значення enum пояснювались лише Python-коментарями в схемі, яких модель не бачить. У v2 кожне значення описано з прикладами Power Platform.
2. **Покращення v2 — не лише підгонка під golden set.** На 30 текстах поза golden set (еталону немає, тож дивимось на індикатори):

   | Індикатор | gpt v1 → v2 | qwen v1 → v2 |
   |---|---|---|
   | `components` порожні | 12/30 → 2/30 | 8/30 → 0/30 |
   | `severity` без явної оцінки | 13/30 → 7/30 | 11/30 → 4/30 |
   | GitHub-тексти з вигаданим середовищем | 7/17 → 2/17 | 16/17 → 9/17 |
   | розпізнано `alm_tooling` (pac CLI) | 0/30 → 6/30 | 0/30 → 9/30 |

3. **100% валідного JSON у всіх прогонах зі схемою.** Strict structured output (OpenAI) і схема в `format` (Ollama) обмежують генерацію, тож repair не знадобився жодного разу. Без схеми (json-mode) з'явився 1 repaired із 40 — валідація і repair потрібні як страховка.
4. **Семплінг B (t=0.7) не дає виграшу.** Для gpt-4o-mini — стабільно трохи гірше (−0.02…−0.03); для qwen v2 різниця в межах шуму (+0.01). Для extraction потрібна відтворюваність, тому t=0.
5. **v2 дорожчий на 26%** ($0.52 → $0.66 / 1000 док.) через довший промпт. Цікаво, що з тим самим промптом v1 gpt-4o-mini рахує в середньому 2 773 вхідних токени, а qwen — 405. Токенізатори різні, але різниця в ~7 разів, найімовірніше, пояснюється JSON-схемою з описами полів, яку OpenAI в strict-режимі додає до промпту. Тобто описи полів у схемі — головний «важіль» вартості (перевірити, скоротивши описи).
6. **gpt-4o-mini у ~3× швидший** (p50 2.5 с проти 8.3 с) і має значно стабільніший p95 (3.8 с проти 19.4 с) — локальна 7B-модель на ноутбучній GPU повільніша на довгих GitHub-текстах.

## 4. Розбір характерних помилок (фінальний v2, семплінг A)

| # | Документ | Що замість чого | Чому |
|---|---|---|---|
| 1 | syn-009 «задачі з ЛЕО не підтягуються… з 12.10» | **qwen:** `release_version: "12.10"` замість `null`; **обидві:** `is_regression: null` замість `true` | Дата «12.10» має формат версії — менша модель плутає їх. Неявна регресія («з 12.10 перестало») без слів «раніше працювало» не розпізнається навіть з прикладами в промпті |
| 2 | gh-005, довгий шаблон CoE Kit зі списком дій | **qwen:** 10 компонентів (дії всередині flow `List_Envt_BPFs`, `List_Envt_MDApps`… як окремі flows, з дублікатами) замість 2 flows; `environments: [dev, test, uat, prod]` замість `[]` | Правило v2 «кожен названий компонент — окремий елемент» менша модель застосовує буквально: не відрізняє flow від дії в ньому. Довгий текст «розмиває» правило про середовища — модель заповнює всі 4 |
| 3 | gh-005, у тексті «4.5.0» в описі і «4.50.0» у полі шаблону | **gpt:** `release_version: "4.5.0"` замість `"4.50.0"` | Неоднозначне джерело: модель бере першу згадку, а правило розмітки — довіряти полю шаблону. Правило є і в промпті v2, але конфлікт двох версій у тексті модель не помічає |
| 4 | syn-001 `Severity: High`; syn-010 без оцінки | **qwen:** `critical` замість `high`; `critical` замість `null` | qwen гірше дотримується інструкцій: «підсилює» серйозність через слова на кшталт «Something went wrong», «дубль інвойсу», ігноруючи явну мітку й правило «емоції ≠ severity». gpt-4o-mini на v2 — 1.00 по severity |
| 5 | syn-007 «щось не так з звітами. цифри не сходяться» (json-mode) | **qwen без схеми:** спершу `is_defect: null` → помилка валідації → repair → `is_defect: false`, хоча це скарга на некоректні дані, тобто дефект | Без схеми в `format` модель лишає `null` у bool-полі, коли не може вирішити. Repair виправив **форму**, але не **зміст**: модель просто вибрала одне з дозволених значень. Висновок: валідація гарантує структуру, а правильність перевіряє лише golden set |

**Обмеження метрики, помічене під час розбору.** Частина «помилок» `actual_result` у gpt-4o-mini — це коректні, але скорочені формулювання (syn-005: «міссінг депенденсі на таблицю cnt_invoice» проти довшого еталону) — метрика покриття слів ≥ 50% їх не зараховує. Реальна точність цього поля вища за 0.70; для наступних кейсів варто LLM-judge або семантична схожість. Також qwen іноді повертає рядок `"null"` замість `null` у `name` і `"1.5.1 (hotfix)"` замість `"1.5.1"` — це виправляється простим пост-процесингом.

## 5. Вибір для продакшну

**gpt-4o-mini + промпт v2 + семплінг A (t=0).** Найвища точність (0.91 проти 0.73 у найкращої локальної конфігурації), 100% валідних відповідей, p95 < 4 с і вартість ~$0.66 на 1000 баг-репортів — для команди, яка отримує сотні баг-репортів на місяць, це центи. Температура 0 дає відтворювані результати, а strict structured output гарантує форму JSON; Pydantic-валідація з однією спробою repair лишається як страховка.

**За яких умов я б змінила рішення:**
- **Конфіденційність.** Якщо баг-репорти містять дані клієнтів і політика компанії забороняє зовнішні API — локальна qwen2.5:7b + v2 (0.73) з пост-процесингом, або більша локальна модель (14B) на сервері з GPU, після повторних замірів на golden set.
- **Обсяг і вартість.** При мільйонах документів (наприклад, міграція архіву тікетів) — скоротити описи в схемі (основна частина вхідних токенів), перевірити кешування промпту, або перейти на локальну модель для пакетної обробки, де latency не критична.
- **Якість.** Якщо на розширеному golden set (20+) точність gpt-4o-mini впаде нижче ~0.85 або з'являться систематичні помилки — порівняти з дорожчою провайдерською моделлю тим самим `make run`.
- **Доступність.** Недоступність OpenRouter/OpenAI — fallback на локальну модель через той самий інтерфейс `LLMClient` (змінюється лише конфіг).

## 6. Обмеження та чесні застереження

- **Golden set малий (10).** Один документ = 10% точності по полю; різниця < 0.05 між конфігураціями — у межах шуму.
- **Правила v2 виведено з помилок на golden set.** Тому приріст може бути трохи завищеним. Пом'якшення: приклади в промпті навмисно не з golden set; покращення підтверджено індикаторами на 30 текстах поза ним (розділ 3.3).
- **Один прогін на конфігурацію.** Для t=0.7 результат між запусками варіюється; дисперсію не заміряно.
- **Синтетичні дані згенеровано моделлю Claude.** Claude не є жодною з порівнюваних моделей, тож прямого «впізнавання власного стилю» немає; половина даних — реальні GitHub-тексти.
- **Метрика текстових полів груба** (покриття слів) — див. розділ 4.

## 7. Як відтворити

```bash
pip install -e ".[dev]"
cp .env.example .env          # OPENROUTER_API_KEY=...
ollama pull qwen2.5:7b-instruct
python main.py run                                   # v2 (production), обидві моделі × A, B
python main.py run --prompt extract_defect/v1        # baseline
python main.py run --models local_json --sampling A  # контроль: без схеми, repair
python main.py eval                                  # → results/metrics.md, metrics.csv
python -m pytest -q
```

Кожен запис у `results/*.jsonl` містить модель, версію і хеш промпту, параметри семплінгу, статус (`ok` / `repaired` / `failed`), кількість спроб, токени, latency, вартість і сам JSON.
